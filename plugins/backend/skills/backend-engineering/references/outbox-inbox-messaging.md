# Outbox, Inbox and Messaging

> **Golden path:** Write the event row in the same transaction as the state change, run exactly one relay, deliver at-least-once, and make every consumer idempotent with a unique (message id, consumer) marker.

## 1. When this applies

- A state change must be announced to another module, service or broker.
- You are building or reviewing an event relay (CDC connector or polling publisher).
- You are writing a message consumer, or any handler that can be delivered the same message twice.
- You are adding a second producing module to a system that already has one.

Status legend used below: `[shipped]` exists in the reference system, `[proposed]` is a design the reference system is moving toward (uncommitted work in progress), `[known gap]` is a verified hole in the reference system. Do not present `[proposed]` or `[known gap]` items as proven patterns.

## 2. Principles

- **Never dual-write.** The state change and the event row commit in one database transaction. A separate relay moves the row to the broker.
- **Delivery is at-least-once, effect is exactly-once.** The relay may publish twice; the consumer makes the second delivery harmless with a unique marker committed in the same transaction as the effect.
- **Enqueue never saves.** Writing an outbox row only adds it to the unit of work. The caller's single save commits state and event together.
- **Run exactly one relay.** CDC and polling publish the same rows; running both double-publishes.
- **Message identity survives every hop.** Message id, correlation id, causation id and trace parent are written into the outbox row at write time and restored from headers at consume time.
- **Silent failure is the failure mode.** Every trap below produces no error, only an empty consumer. Design the checks that make them loud.

## 3. Design

### Producer side [shipped]

```
handler(command):
    aggregate = load_or_create(command)          # state change
    outbox.enqueue(event_for(aggregate))         # adds a row to the unit of work, NEVER saves
    unit_of_work.save()                          # one transaction: aggregate row + outbox row
```

Outbox row columns: `id` (equals the message id, time-ordered UUID), `aggregate_type` (topic routing), `aggregate_id` (broker partition key, gives per-aggregate ordering), `event_type`, `payload` (json), `occurred_on`, `processed_on` (null until relayed), `correlation_id`, `causation_id`, `trace_parent`. The last three are captured from the ambient trace context at write time, not threaded through call sites.

- **One outbox table per module, in the module's own schema.** The writer is bound to one database context, because the row must land in the same context whose save commits the state change. Why per-module ownership and keyed registration are the rule for every module-scoped service is in `architecture-modular-monolith.md`.
- **The row id is assigned by the application.** Configure the id column as "never generated by the database", otherwise the database may override the message id and break dedup downstream.
- **With derived snake_case naming the primary key column is `id`** (lowercase). Any connector field mapping must say `id`, not `Id`.

### Relay choice: CDC or polling [shipped]

A single setting selects the relay (`relay = cdc | polling`); the default is CDC. Both emit an identical wire format: topic `{prefix}.{aggregate_type}.events`, key = aggregate id, value = raw JSON payload (no envelope), headers `MessageId`, `CorrelationId`, `causationId`, `traceparent`, `eventType`.

### Polling relay: claim, publish, complete [shipped]

```
loop:
    # 1. CLAIM: one auto-committed statement, lease a batch
    rows = UPDATE outbox SET locked_until = now() + lease, attempts = attempts + 1
           WHERE id IN (SELECT id FROM outbox
                        WHERE processed_on IS NULL AND (locked_until IS NULL OR locked_until < now())
                        ORDER BY occurred_on LIMIT n
                        FOR UPDATE SKIP LOCKED)
           RETURNING *

    # 2. PUBLISH: no database connection held across the broker round trip
    acked_ids = publisher.publish_batch(rows)       # returns ONLY acknowledged ids

    # 3. COMPLETE: short second statement
    UPDATE outbox SET processed_on = now() WHERE id IN (acked_ids)
```

- Reference defaults, all configurable: lease 30 s, batch 100 rows, poll interval 2 s when a poll found nothing (verified in the relay options).
- `SKIP LOCKED` lets several relay instances run without contention.
- A failed publish keeps its lease and becomes eligible again when the lease expires. A crashed relay heals itself the same way.
- A partial index on pending rows (`ON outbox (occurred_on) WHERE processed_on IS NULL`) serves the claim query.
- **Pipeline the produce.** Enqueue the whole batch with the producer, then await the delivery reports concurrently and collect the acknowledged ids. Awaiting each row in turn turns 100 rows into 100 serial round trips and defeats the client's batching.
- **Producer settings:** `acks = all`, idempotence on, key = aggregate id (keeps per-key ordering), small linger plus compression for batching.

### CDC relay (Debezium-style) [shipped]

The connector captures the outbox table and an event-router transform turns each row into a message. Required configuration:

- **Expand the json payload.** A `jsonb` column is captured as an escaped string. Without `expand json payload = true` the message value is a double-encoded string literal, a raw-JSON consumer cannot bind it, faults the message, and the only symptom is an empty inbox. Set it in the production connector and in the test fixture.
- **Header mapping must match what the consumer reads:** `id -> MessageId`, `correlation_id -> CorrelationId`, `causation_id -> causationId`, `trace_parent -> traceparent`, `event_type -> eventType`.
- **Publication mode `filtered`**, not `all_tables`. The default streams the write-ahead log of every table.
- **The include list must name the outbox of every producing module.**

### Consumer side [shipped]

```
on_message(msg):
    restore_context(msg.headers)        # re-parent trace from traceparent; copy correlation/causation to ambient context
    inbox.try_consume(msg.message_id, consumer_name, work = () -> effect(msg))

try_consume(message_id, consumer, work):
    if exists(marker(message_id, consumer)): return false          # fast path, an optimization only
    add marker(message_id, consumer)                                # composite primary key
    work()                                                          # mutates the SAME context
    try: save()                                                     # marker + effect, one transaction
    catch unique_violation(23505): clear_tracked_state(); return false   # lost the race: a duplicate, not an error
    return true
```

- **Start new consumer groups at the earliest offset.** The broker default is "latest", so a fresh or restarted group silently skips every event produced before it joined.
- **Use raw JSON deserialization** (no message envelope), because the relay emits plain JSON.
- **Identity is read natively from `MessageId` and `CorrelationId` headers.** Both must parse as UUIDs, otherwise the library silently yields null. Correlation ids are therefore UUID-only by design.
- **The messaging library does not read W3C `traceparent`**, only its own proprietary header. A small consume filter must re-parent the span from `traceparent` and copy correlation and causation ids into ambient context and span tags. Without it, producer and consumer are two unrelated traces.
- Pin the messaging library to the last open-source major line; bump deliberately, not through dependency automation.

## 4. Traps

- **Unkeyed outbox writer.** With one writer registered unkeyed and two producing modules, the last registration wins. A handler in module A silently writes its row into module B's context, where it is never saved. The broker never sees it and the inbox stays empty. Register the writer keyed by its database context and inject it by that key. Found when the second producing module broke the end-to-end test.
- **Connector include list drift [known gap].** The reference connector config lists only `platform.outbox`, while the Events module also has an outbox. Under the default CDC relay, Events integration events never reach the broker, and no test catches it. The connector README even shows a wrong schema name in its example. Cautionary rule: every module that gets an outbox gets a connector entry in the same change, and a test (which the reference system lacks, `[proposed]`) asserts that the include list equals the set of module outboxes.
- **Connector registered before the table exists.** With `filtered` publication mode the publication is created at connector start. If migrations have not run, the task fails with "No table filters found for filtered publication" and never recovers. Zero CDC, silent. Immediate fix: restart the connector task after the table exists, then verify the publication and an active replication slot. Durable fix: a one-shot `schema-ready` step that polls for the table before the connector starts. Test fixtures migrate before registering the connector.
- **Readiness depends on the CDC connector, connector waits on readiness.** Deadlock. What the reference system actually does (verified): the `ready` probe **does** include the CDC connector's URL (alongside database, cache, broker and the shutdown check), and "migrations applied" sits in a separate **startup** probe that the connector gates on. The deadlock was broken by moving migrations out of readiness, not by removing the dependency. So the precise rule is: **the connector may gate on the startup probe only; it must never gate on a probe that includes the connector.**
- **Readiness that probes the CDC connector turns a CDC outage into an HTTP outage.** When the connector is down, readiness fails and the load balancer pulls every instance, although the API itself (which only writes outbox rows) is perfectly able to serve. Question whether the connector belongs in readiness at all; a lagging or down relay is better surfaced as an alert on outbox age and unprocessed-row count. The reference system accepts the coupling `[known gap, debatable]`.
- **Post-commit domain events are not durable.** They live in memory between commit and publish; a crash loses them. Anything that must happen goes through the outbox.
- **Fast-path duplicate check is not the guard.** Two concurrent deliveries both pass the `exists` check. Only the unique constraint decides. Without the unique-violation catch, concurrent duplicates become a poison loop that retries forever.
- **Work must mutate the same context as the marker**, or atomicity is lost.
- **Per-row awaits defeat batching** (see pipelined produce above).
- **Both relays enabled.** Double publish. Make the setting mutually exclusive and assert it at startup.
- **Pub/sub or best-effort signals are not delivery.** Use the outbox for anything with a consequence.
- **Pin the CDC connect image**; it has no stable `latest` tag.
- **Shell path rewriting on Windows** can mangle `docker exec` paths and fail silently when stderr is discarded. Disable path conversion for those commands.
- **Dead-letter handling and sagas [known gap].** The reference system has no dead-letter topic handling beyond the library's default fault behavior and no process manager or saga. Do not assume them; add them before depending on multi-step compensation.
- **No cross-module consumer exists yet [known gap].** The integration-event contract has no subscriber; the end-to-end test proves the spine with a module consuming its own event.

## 5. Invariants to test

- **Atomicity:** a command produces the aggregate row and the outbox row in one transaction; a failing save leaves neither.
- **Keyed writer:** the writer injected into module A's handler resolves to A's context. `[proposed]` An architecture rule forbids injecting an unkeyed writer; the reference system's five architecture tests are dependency-direction rules only, and the keyed writer is protected today by the end-to-end spine test failing when the second producing module is added.
- **Claim:** a claimed row is marked processed; a second poll never relays it; a failed publish leaves the row leased and unprocessed, and an immediate re-poll skips it. Needs a real database, because `SKIP LOCKED` cannot be faked in memory.
- **Partial failure:** the publisher returns only acknowledged ids.
- **Wire-format parity:** the polling relay builds topic, key, value and headers byte-identical to what the CDC router produces. Use the production connector file verbatim in the test fixture, so configuration cannot drift.
- **Inbox idempotency:** 20 parallel deliveries of one message produce exactly one `true`, no exceptions, one marker row, one effect row.
- **End to end:** HTTP request, outbox row, CDC, broker, consumer, inbox row, with trace and correlation ids intact. Poll with a deadline; never sleep and hope.
- **Include list** `[proposed]`: the connector include list contains every module's outbox table. Not a test today: the integration fixture registers the production connector file and only asserts that the connector reaches `RUNNING` (verified), which passes with an incomplete list. Add a test comparing the include list against the set of module outbox tables.
- **Startup order:** migrations run before the connector registers, in the test fixture and in compose.

## 6. Rationalizations / Red flags

| Rationalization | Reality |
|---|---|
| "I'll publish to the broker right after the save" | The process can die between the two. That is a dual write. |
| "The broker guarantees exactly-once" | Not across a consumer crash. Ack and side effect are not one transaction. |
| "I check `exists` before inserting the marker" | Check-then-act is a race. The unique constraint is the guard. |
| "Both relays on is safer" | It double-publishes every event. |
| "One shared outbox table is simpler" | It couples module schemas and breaks per-module connector control. |
| "Domain events are enough, they fire after commit" | They are in memory. A crash loses them. |

Red flags in a diff: an unkeyed writer registration; `save()` inside an enqueue method; a handler that awaits a broker call; a consumer without a unique-violation catch; a new module outbox with no connector entry; `latest` offset reset; a correlation id that is not a UUID.

## 7. Checklist

- [ ] State and outbox row commit in one save; enqueue never saves.
- [ ] Writer is keyed per context; row id is application-assigned.
- [ ] Exactly one relay is enabled; the choice is asserted at startup.
- [ ] Connector include list covers every module outbox; json payload expansion is on.
- [ ] Connector starts only after the tables exist; it gates on the startup probe, never on a probe that includes the connector; the readiness-includes-connector coupling is a conscious decision.
- [ ] Consumer uses a `(message_id, consumer)` unique marker in the effect's transaction and treats unique violation as a duplicate.
- [ ] Consumer restores trace, correlation and causation from headers; offset reset is earliest.
- [ ] Wire-format parity and inbox-concurrency tests exist and run against real infrastructure.
