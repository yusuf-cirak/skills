# Error Model

> **Golden path:** Expected failures are values with code, message and status, mapped to the wire format in exactly one place; exceptions are for bugs and invariant violations.

## 1. When this applies

- Deciding how a function reports failure (value vs exception).
- Adding validation, a not-found/conflict path, or a new pipeline step that can reject.
- Defining or changing the wire error format.
- Reviewing code that returns null, an empty string or a magic value to mean "absent" or "failed".

Contract-level rules (consistent shape across endpoints, error codes as part of the API) are in the installed `api-and-interface-design` skill; this file is the implementation model behind it.

## 2. Principles

1. **Expected failures are values in the signature.** Validation errors, not-found, conflict, forbidden are normal outcomes. They are returned, not thrown, so the compiler or type checker forces every caller to handle them.
2. **Exceptions are for bugs and unrecoverable faults.** Programmer errors, broken invariants and infrastructure faults throw; they map to a generic 5xx.
3. **An error is data: stable code, human message, transport status.** The code is machine-readable and part of the public contract (a code, once published, is a Hyrum's-law commitment). The transport status is chosen where the error is created, not guessed at the edge.
4. **Absence is explicit.** Use an option type for "may not exist". Never use null, an empty string or a zero as an in-band "nothing".
5. **One mapping point.** Exactly one place converts failure values into the wire format. Handlers, behaviors and endpoints never format errors themselves.
6. **Pipeline steps fail through the same channel as handlers.** Validation, lock contention and re-authorization return failure values; nothing in the request path has a second error vocabulary.
7. **Security invariants still throw.** A violated invariant that indicates a bug or an attack (cross-tenant write, tenant-less write) is not a business outcome and must not be recoverable by a caller who ignores a return value.
8. **Never leak why.** Authentication failures and 5xx responses carry no internal detail in production.

## 3. Design

### Types

```
Result<T>     = Success(value) | Failure(Error)
Result        = Success | Failure(Error)         # no payload
Option<T>     = Some(value) | None
Error         { code: string, message: string, status: int }      # status 0 -> treated as 500 at the mapper
ValidationError : Error { fields: map<fieldName, list<message>> } # status 400, aggregates every failing rule
```

Use a maintained result/option library (or the language's native sum types) rather than hand-rolling one. Absence example: the current-user port returns `Option<UserId>`, not an empty string, so "anonymous" cannot be confused with a user whose id is blank. [shipped]

### Where failures are created

```
domain factory      -> Failure(validation/conflict code)           # business rules
validation step     -> Failure(ValidationError)                    # request shape, every validator, aggregated
lock step           -> Failure(conflict, 409)
sensitive step      -> Failure(unauthorized, 401)
handler             -> Failure(not-found / conflict / ...)
```

The validation step does not throw. It builds a failure of the handler's response type and returns it; the endpoint mapper renders it. Older guidance that "validation exceptions map to 400 in a global handler" describes the previous design and is stale.

### The single mapper (failure to problem document, RFC 9457)

```
toApiResult(result):
  if success: return 200/201/204 with value
  err = result.error
  if err is ValidationError: return problem(400, type=validation, errors=err.fields)
  status = err.status != 0 ? err.status : 500
  return problem(status, title=err.message, extensions={ code: err.code })
```

Rules of the problem document:

- Machine-readable `code` is an extension field. Clients switch on `code`, never on message text.
- A customizer stamps `instance`, `traceId` and `correlation_id` on every problem response, including those generated by the framework (404 routing, 415, auth), so support can always join a user report to a trace.
- In production the detail of 5xx is hidden; the trace id is the handle.
- Authentication and authorization failures return problem documents with failure detail suppressed (no "signature invalid" vs "expired" distinction).
- If the response has already started streaming, do not try to write an error body (it corrupts the stream); let the connection reset.
- A client that disconnects triggers a cancellation. Map it to status 499 and do not log it as an error.

### Exceptions that stay

```
global exception handler : unexpected -> 500 problem, logged with trace; never leaks message in prod
save interceptor (tenant): no ambient tenant on a tenant-owned write  -> throw
                           cross-tenant write                           -> throw
```

These are deliberate: they are bugs or attacks, and the safest behavior is that execution cannot continue.

### Fail-open and fail-closed

Which dependencies may degrade and which must reject is a named list that lives in one place: `resilience-lifecycle.md`. Every new failure value for "dependency unreachable" must say which side of that list it falls on.

## 4. Traps

- **Result-returning handlers only.** The validation step needs to build a failure of the handler's own result type. A handler returning a bare value throws at the first rejection. Enforce at compile time if the type system allows, otherwise test every validated use case with invalid input.
- **Status guessed at the edge.** If the mapper infers the status from the message, a reworded message changes the HTTP code. The status is part of the `Error` value.
- **Two error vocabularies.** If some pipeline steps throw and others return failures, every caller has two paths and one of them gets forgotten. Keep one.
- **null/empty sentinels.** A `""` current-user id once meant "anonymous"; it was replaced by an option type. Any new "empty means none" is the same bug.
- **Echoing client-supplied ids into error text** can leak or inject. Include only server-generated ids in messages, and validate any inbound correlation id strictly (UUID-only) before echoing it in a header.
- **Catch-all `catch` that swallows.** A handler that catches everything and returns a generic failure hides bugs from the exception handler and from alarms.
- **Mixing domain errors and transport concerns.** The domain creates errors with a status because the status is part of the contract, but it never builds a response document.
- **Framework-generated errors that bypass the format.** Routing 404, body-too-large, unsupported media type must go through the same customizer or clients see two shapes.

## 5. Invariants to test

- Invalid request returns the failure with a field-to-messages map (validation step test); a request with no validators passes through.
- Mapper: validation error renders 400 with `errors`; an error with a status renders that status; an error with status 0 renders 500; `code` is present in extensions.
- Every problem response, including a framework-generated 404 and 415, has `traceId` and `correlation_id`.
- 5xx body contains no exception message when the environment is production.
- Revoked token returns 401 though signature and lifetime are valid.
- Tenant guard tests: tenant-less write and cross-tenant write throw (they are not returned as values).
- Grep or architecture rule: no `throw` in domain or application except for programmer errors and the named security invariants.
- Client abort produces 499 and no error-level log line.

## 6. Rationalizations / Red flags

| Rationalization | Reality |
|---|---|
| "Throw NotFound, the global handler will map it" | Every caller must now know it can throw. Return a failure. |
| "Null is fine for 'not found'" | Null cannot say why, and it propagates. Option plus explicit failure. |
| "We'll format the error in the controller for now" | Now there are two formats. One mapper. |
| "Show the exception message to help debugging" | In production it leaks internals. Trace id is the handle. |
| "Return an empty string, it's simpler than an option" | The empty string is a valid value for something else one day. |

Red flags: `catch (everything)` with a bare return; a new error without a stable code; a response body built by hand; a message used as a key by a client; 4xx and 5xx rendered by different code paths; an error carrying an internal stack trace outside development.

## 7. Checklist

- [ ] Expected failures are `Result`/`Option` values; exceptions only for bugs and named security invariants.
- [ ] Every error has a stable code, a message and a status chosen at creation.
- [ ] One mapper renders the wire format; framework errors go through the same customizer.
- [ ] `traceId` and `correlation_id` on every problem; 5xx detail hidden in production.
- [ ] Validation fields aggregated, not first-error-only.
- [ ] Mid-stream failure and client abort handled without corrupting the response.
- [ ] Each "dependency unreachable" failure is placed on the fail-open or fail-closed list (`resilience-lifecycle.md`).
